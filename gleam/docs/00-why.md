# 00. なぜ今 Gleam を学ぶのか

## 位置づけ

Louis Pilfold が 2016 年に始め、2024 年に 1.0 に到達した言語。
Erlang VM (BEAM) 上で動き、Erlang / Elixir のライブラリと相互運用できる。JavaScript にもコンパイルできる。
Rust 風の構文、ML 系の型推論、Erlang の実行モデルを組み合わせている。

## 差がつくポイント

- **OTP を型付きで学べる**: Erlang / Elixir の並行モデル (プロセス、メッセージ、監視ツリー) は 30 年の実績があるが、動的型のため大規模化で辛い。Gleam はメッセージを `Subject(msg)` で型付けし、間違った型のメッセージ送信をコンパイル時に弾く。
- **言語が小さい**: `if` / ループ / 例外 / null / 継承がない。`case`、再帰、`Result`、`use` で全部書く。1 日で言語仕様を読み切れる。
- **JavaScript ターゲット**: 同じコードがブラウザと Node で動く (OTP 以外)。Lustre (Elm 風フロントエンド) がある。
- **エラーメッセージ**: Elm / Rust 系の丁寧なエラー。学習中に詰まりにくい。
- **Hex エコシステム**: Erlang / Elixir のパッケージをそのまま使える。

## 向いている用途 / 向いていない用途

| 向いている | 向いていない |
|---|---|
| Web バックエンド、リアルタイム通信、並行処理の多いサーバ | 数値計算・低レイヤ (BEAM は速くない) |
| Elixir / Erlang を型付きで書き直したい | GUI、モバイル |
| 「小さい言語」で関数型と並行処理を学びたい | 巨大なエコシステムが前提の開発 (まだ若い) |

## 他の言語との比較

Elixir とはランタイムを共有し、Elixir のマクロと動的型の代わりに、Gleam は静的型と小さな構文を選んだ。
Rust とは構文が似ているが、所有権はなく GC (BEAM のプロセス単位 GC) がある。
Go の goroutine + channel と比べると、BEAM のプロセスは監視・再起動 (let it crash) の仕組みが標準にある。
