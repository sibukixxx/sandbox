# 00. なぜ今 Rust `no_std` を学ぶのか

## 位置づけ

`no_std` は Rust の機能ではなく「標準ライブラリを使わない書き方」。
`std` は OS (Linux, Windows, ...) を前提にしているので、OS のない環境 (ベアメタル、組込み、カーネル、WASM ランタイム、ブートローダ) では `core` と `alloc` だけで書く。

## 差がつくポイント

- **Rust は普及したが、`no_std` を書ける人はまだ少ない**。組込み (embedded-hal)、Linux カーネル (Rust for Linux)、Windows カーネル、スマートコントラクト、WASM コンポーネントなど、需要は増える一方。
- **`std` が隠していたものが見える**。ヒープ、スレッド、I/O、パニック処理、エントリポイントが「OS からもらっていたもの」だと分かり、通常の Rust の理解も深まる。
- **`std` / `no_std` 両対応クレートの書き方** (feature フラグ、`alloc` の段階的有効化) はライブラリ作者に必須。
- Rust の標準ライブラリの大部分 (`Option`、`Result`、イテレータ、`fmt`、スライス) は実は `core` にあり、`no_std` でもほぼそのまま使える。

## 向いている用途 / 向いていない用途

| 向いている | 向いていない |
|---|---|
| マイコン (Cortex-M, RISC-V, ESP32) | 通常のアプリケーション開発 |
| OS カーネル、ブートローダ、ファームウェア | ヒープや OS 機能を前提とするライブラリ |
| WASM ランタイム上の軽量モジュール | Rust をまだ知らない段階 |
| どこでも動くコアライブラリ | |

## 他の言語との比較

C は最初から「OS なし」で書けるが、安全性がない。Rust `no_std` は C と同じ土俵で、所有権による安全性を保つ。
Zig も同じ領域を狙うが、Rust の方がエコシステム (embedded-hal, probe-rs) が成熟している。
